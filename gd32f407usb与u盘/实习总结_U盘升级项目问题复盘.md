# 实习项目复盘：GD32F407 基于 USB Host 的 U 盘升级

> 用途：实习总结 / 面试应答材料。建议先通读一遍，再对着「面试问答」小节做口头复述练习。
> 项目路径：`E:\Shixi\实习成果备份区\gd32f407usb与u盘`

---

## 一、项目一句话简介

在 **GD32F407ZGT6** 上实现"把 U 盘插入板子 → 自动读取 U 盘里的 `firmware.bin` → 写入外部 SPI Flash（W25Q128）→ 复位 → Bootloader 搬运固件到内部 Flash"的完整升级链路，属于嵌入式设备常见的 **IAP（In-Application Programming，在应用编程）** 方案。

## 二、项目背景与我的角色

- **参照原型**：团队里已有一份 **STM32F407** 的可行性验证版本，U 盘升级功能正常。
- **我的任务**：把整套方案 **移植到 GD32F407**（国产芯片，USB 外设从 ST 的 OTG_FS 换成了 GD 的 USBFS，固件库从 ST 标准外设库换成 GD32F4xx_usb_library）。
- **结果**：移植后 U 盘升级**失败**，经过定位后修复，最终功能可用。

一句话概括我的价值：**不是简单照抄代码，而是发现"照抄"本身不成立——GD32 的 USB 外设和复位机制与 STM32 有本质差异，必须针对性地改架构。**

## 三、问题现象（我亲眼看到的）

升级过程中的串口日志给出了三条关键线索：

1. **CSW 解码失败**：
   ```
   [DISK] bot.st=1 cmd=1 xfer_in=0 urb_in=1 urb_out=1
   [DISK] CSW: 00 00 00 00 00 00 00 00 00 00 00 00 00
   ```
   CSW（Command Status Wrapper，命令状态包）全 0、`xfer_in=0`、`urb_in=1(URB_DONE)` —— 即 USB 主机侧 URB 标记为完成，但**一个数据字节都没收到**。

2. **BOT 状态机卡死**：
   ```
   us=5   // MSC_REQUEST_SENSE，单元状态卡死在请求检测命令
   ```
   BOT（Bulk-Only Transport）状态机不再回到 `MSC_IDLE`，软件复位 BOT 也无法恢复。

3. **升级完成跳转时板子完全卡死**，必须重新烧录 Bootloader（等价于强制复位）才能继续。

---

## 四、排查过程（展示思路，面试加分点）

我采用的思路是**逐层收敛**：先看现象 → 定位到具体协议层 → 再下钻到硬件状态：

1. **第一层：读失败位置**。通过打印 MSC 枚举参数（capacity、block size）确认枚举成功；通过引导扇区（0 扇区）预读确认"读"这个动作本身的问题范围。
2. **第二层：BOT 状态机**。发现 `us=5`（REQUEST_SENSE）——说明之前某个命令失败，状态机走到错误恢复分支就再也回不去。
3. **第三层：CSW 解码**。日志显示 CSW 全 0 + URB_DONE 但无数据 → 指向"传输完成标志与真实数据不一致"。
4. **第四层：硬件通道**。发现 BOT reset 后 `urb_in=0`（URB 从未完成）→ 说明**软件层面的重置已无法恢复，USBFS 硬件通道状态损坏**。
5. **关键转折**：把读改成"单扇区 vs 多扇区"的 LBA 扫描探测，配合对升级流程时序的审视，最终锁定真正的触发条件——**不是"某个坏扇区"，而是"擦除期间 USB 长时间停摆"**。

---

## 五、根因分析（核心技术点，面试重点）

### 根因 1：升级期间"边读 USB 边擦 SPI Flash"破坏了 USB BOT 状态机

**背景知识——BOT 协议**：U 盘（MSC 类设备）走 Bulk-Only Transport 协议，一次读命令分三个阶段：CBW（命令包，主机→设备）→ DATA（数据传输）→ CSW（状态包，设备→主机）。只有 CSW 正确收到，状态机才回到 `MSC_IDLE`，才能发下一条命令。

**触发链条**：
1. 原实现 `Upgrade_Execute()` 采用"边擦除边读"：读一部分固件 → 擦 W25Q128 一个 64KB 块（**耗时 150ms~2s**）→ 再读下一部分。
2. 擦除期间，升级流程是**同步阻塞**的，USB 主循环（`usbh_core_task`）和中断轮询停摆。
3. 擦除结束后第一次 8 扇区读，CSW 阶段 URB 标记完成（`urb_in=1`）但实际 0 字节（`xfer_in=0`）→ CSW 全 0 → 解码失败。
4. 失败后单元状态卡在 `MSC_REQUEST_SENSE`（`us=5`），**软件重置 BOT 也无法恢复**——因为 USBFS 硬件通道（FIFO/传输状态）已经损坏，软件层重置只清了协议层状态，没恢复硬件通道。
5. 于是重试也全部失败 → 表现为"读固定 LBA（31656）必失败、capacity 读成 0、引导扇区读失败"。

**一句话根因**：**在 USB 事务进行期间让主机侧长时间停摆（秒级），USBFS 硬件通道状态被破坏且不可自愈。**

### 根因 2：GD32 的 USBFS 在 Host 模式下阻塞软复位

**现象**：升级完成跳转 Bootloader 时板子卡死，必须重新烧录。

**原因**：GD32 的 USBFS 在 Host 模式下会**阻塞 `NVIC_SystemReset` 和 FWDGT（看门狗）**——写复位寄存器不生效。STM32 的 OTG_FS 没有这个问题，所以 STM32 版"NVIC 软复位 + IWDG 兜底"的策略直接搬到 GD32 上行不通。

**一句话根因**：**两个芯片厂商的 USB 外设与复位机制存在差异，移植时必须重新设计复位路径，不能照搬。**

### 附带发现：移植层的 API 差异（属适配，不是 bug）

| 层面 | STM32 参照版 | GD32 当前版 |
|---|---|---|
| Host 库 | USB Host Library v2.1.0（`USB_OTG_CORE_HANDLE`+`USBH_HOST`） | GD32F4xx_usb_library v3.x（`usbh_host`+`usb_core_driver`） |
| 读写接口 | `USBH_MSC_HandleBOTXfer` 轮询 + 回调内升级 | `usbh_msc_read/write` 原始阻塞方式，回调只置标志，升级在主循环执行 |
| MSC 参数 | `USBH_MSC_Param` 全局变量 | `usbh_msc_lun_info_get()` 查询 |
| 连接判断 | `HCD_IsDeviceConnected()` | `usbh_core.host.connect_status` |

## 六、解决方案

### 方案 1：升级流程改为"先整包读入 RAM，再擦写"（解决根因 1）

代码改动位置：`src/usb_host_task.c` + `src/upgrade.c`。

1. 新增 `Upgrade_ExecuteBuf(const uint8_t *fw, uint32_t fw_size)`：接收**完整固件缓冲**，函数内只做擦除 + 写入 + 校验 + 写升级标志，**完全不触碰 USB**。
2. `USB_Host_Do_Upgrade` 改为两段式：
   - **阶段 A（USB 活动期）**：`f_open` → 循环 `f_read` 把整个固件读入 96KB RAM 缓冲 → `f_close` → **卸载 FatFS（`f_mount(NULL,...)`），USB 访问彻底结束**；
   - **阶段 B（无 USB 期）**：调用 `Upgrade_ExecuteBuf()` 做擦除 + 写入，此阶段 USB 空闲，状态机不会被破坏。
3. 约束：GD32F407 SRAM≈128KB，固件 >96KB 时**拒绝升级**（当前固件 52KB，够用）。

### 方案 2：复位改为"彻底关 USB → 硬件复位 USBFS → 跳 Bootloader 入口"（解决根因 2）

代码改动位置：`bsp/platform.c` 的 `Platform_SystemReset()`：

```
1) 关 USBFS 中断（nvic_irq_disable）+ 关全局中断（__disable_irq）
2) RCU_AHB2RST |= RCU_AHB2RST_USBFSRST;   // 硬件复位整个 USBFS 外设到上电默认态
3) 跳转到 Bootloader 入口（startup 重新初始化所有外设 = 等效冷启动）
```

原理：跳 Bootloader 与 Bootloader 跳 APP 是同一个机制、方向相反——Bootloader 的启动代码会重新初始化时钟和外设，等同于冷启动，绕开了 USBFS 对软复位的阻塞。

---

## 七、为什么这两个方案能解决问题（讲原理，面试追问必答）

- **方案 1 的本质是"隔离互斥资源"**：W25Q128 的擦除是不可抢占的长时间操作，而 USB 传输要求主机持续轮询（几百微秒~毫秒级不能断）。两者天然冲突。把"读 USB"和"擦写 Flash"**从时间上彻底分开**，让 USB 只在连续、无阻塞的窗口内工作，BOT 状态机就永远有被服务的机会，不会超时/卡死。
- **方案 2 的本质是"绕开芯片级缺陷"**：不跟 USBFS 阻塞软复位的特性硬刚（那可能无解），而是跳到 Bootloader 走它成熟可靠的冷启动路径，复用已有的启动代码，改动最小、风险最低。
- **共同原则**：**不要在一个实时/协议驱动的子系统里做秒级阻塞操作；碰到芯片差异时先确认"能不能复用参照方案的机制"，不行就换一条路。**

## 八、结果与验证

- 修改后 U 盘升级**功能可用**：插 U 盘 → 自动枚举 → 读 `firmware.bin` → 擦写 W25Q128 → 复位 → Bootloader 搬运 → 跳转新 APP 成功。
- 日志验证：升级标志（`UPGRADE_FLAG_YES`）写 SPI Flash 后**回读校验通过**；Boot 扇区 55AA 签名校验 OK；引导扇区与 LBA 扫描探测不再失败。
- 无代码修改需求（本次为复盘，未改任何源码）。

## 九、经验教训（面试谈"收获"用）

1. **移植 ≠ 抄代码**：不同厂商芯片的外设（USB、复位、时钟树）实现差异很大，先做"机制可行性分析"，再谈 API 翻译。
2. **时序与协议状态机是嵌入式的大坑**：任何阻塞操作都要评估它会不会饿死中断驱动的协议栈（USB/BT/CAN 同理）。
3. **日志要打在关键协议层**：正是 `bot.st / cmd / xfer_in / urb_in / CSW` 这种细粒度打印，才把问题从"U 盘读失败"缩小到"CSW 阶段"这一个点。
4. **重试不是万能的**：当"失败后状态卡死、软件重置无效"时，说明损坏在硬件层，继续重试只是浪费，要换思路（隔离 / 硬件复位 / 冷启动）。
5. **方案要带约束意识**：96KB RAM 缓冲上限是我主动识别并写明的 trade-off——面试时主动说出方案的边界，比被追问后承认更加分。

## 十、面试问答（重点演练）

### Q1：简单介绍一下你做的这个项目？
**答**：我在 GD32F407 上实现了基于 USB Host 的 U 盘 IAP 升级。设备插上 U 盘后，固件自动从 U 盘读出、写入外部 SPI Flash，复位后由 Bootloader 搬运到内部 Flash 完成升级。我是从 STM32F407 的可行版本移植过来的，期间发现并解决了两类问题：一是升级流程中 USB 与 SPI Flash 擦除的时序冲突导致 USB BOT 状态机损坏，二是 GD32 的 USBFS 在 Host 模式下阻塞软复位。

### Q2：为什么"边读 U 盘边擦 Flash"会失败？
**答**：W25Q128 块擦除需要 150ms~2s，是同步阻塞操作。这段时间 USB 主循环停摆，主机无法及时轮询 U 盘的 BOT 状态机。擦除结束后第一次读命令的 CSW 阶段，URB 标记完成但实际没有收到数据（日志：CSW 全 0、xfer_in=0、urb_in=1），解码失败后单元状态卡在 REQUEST_SENSE，且失败发生在硬件传输通道层面，软件重置无法恢复。

### Q3：BOT 协议的三阶段是什么？CSW 全 0 说明什么？
**答**：CBW（命令块，主机→设备）→ DATA（数据传输）→ CSW（状态块，设备→主机）。CSW 全 0 说明主机认为传输已完成（URB_DONE）但实际字节数为 0，即传输完成标志与真实数据不一致——典型的硬件通道状态错乱，而非设备没响应。

### Q4：你的解决方案是什么？为什么有效？
**答**：把升级流程改成两段式——先通过 FatFS 把整个固件连续读入 96KB RAM 缓冲，卸载文件系统、结束所有 USB 访问；再调用新的 `Upgrade_ExecuteBuf()` 做擦除+写入，此阶段完全不触碰 USB。本质是把两个互斥的资源（需要持续轮询的 USB 协议栈 vs 不可抢占的 Flash 擦除）在时间上彻底隔离。

### Q5：为什么不做"擦一块、读一块"的流水线？RAM 缓冲限制怎么看待？
**答**：流水线方案仍需在擦除期间暂停 USB 轮询，问题没有本质解决（除非擦除能异步/可中断，比如用状态机把擦除也拆小，但 W25Q128 硬件擦除本身不可中断）。RAM 缓冲方案简单可靠，代价是固件大小受 SRAM 限制（当前 96KB 上限、固件 52KB）。如果以后要支持大固件，可以改成"分段搬运 + 写入阶段由 Bootloader 从 SPI Flash 再搬一次"或者把擦写也做成非阻塞状态机。

### Q6：GD32 和 STM32 移植时最大的坑是什么？
**答**：最大坑是复位机制。STM32 的 OTG_FS 可以直接 NVIC 软复位 + IWDG 兜底；但 GD32 的 USBFS 在 Host 模式下会阻塞 `NVIC_SystemReset` 和 FWDGT，软复位写下去不生效，表现为升级完成后卡死。解决方式是彻底关闭 USBFS（关中断 + 硬件复位外设）后直接跳 Bootloader 入口，让它的启动代码完成等效冷启动。

### Q7：你是怎么定位到根因的？（考察排查思路）
**答**：逐层收敛。先通过枚举参数确认 USB 枚举本身成功；再用引导扇区预读和 LBA 单扇区/多扇区扫描，排除"特定坏扇区"假设；然后盯 BOT 协议层日志（bot.st/cmd/xfer_in/urb_in/CSW），把失败点精确到 CSW 阶段；最后结合升级流程的时序（擦除期间主循环停摆）才锁定根因是时序冲突而非数据/扇区问题。

### Q8：如果面试官问"这个项目你最大的收获是什么"？
**答**：两点。一是学会了**协议驱动系统里时序分析**——嵌入式很多疑难 bug 是"某段代码阻塞了必须被持续服务的子系统"造成的，排查时要同时看协议状态和主循环时序；二是认识到**移植是机制适配，不是 API 翻译**——芯片厂商之间的外设行为差异（如复位、USB）需要先验证机制可行性再动手。
